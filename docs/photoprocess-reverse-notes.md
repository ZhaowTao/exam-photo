# PhotoProcess.exe 逆向笔记

> 记录 2026-10 分析人社部人事考试中心「照片处理工具」的过程与结论。
> 目的只有一个：搞清楚它**到底做了什么校验**，好在非 Windows 系统上产出等价文件。

## 1. 样本

| 项目 | 值 |
|---|---|
| 文件名 | `照片处理工具.exe` |
| 体积 | 约 5 MB |
| 类型 | PE32 executable (GUI), Intel 80386, 32-bit |
| 加壳 | 无。PE 头完整，导入表可读，节区名正常 |
| 编译器痕迹 | MFC42（VS6 时代）、OpenCV 1.0 |
| 版本资源 `FileVersion` | `1.0.0.25` |
| 版本资源 `CompanyName` | 人社部人事考试中心 |
| 附带文件 | `photo.ini`、`使用说明.doc`、`opencv` 相关 DLL |

无壳这一点很关键：不需要脱壳，字符串和导入表直接可读，分析成本从「几天」降到「一小时」。

## 2. 关键字符串

从 `.rdata` 段直接读出的、决定行为的字符串：

```
photo.ini
min_width
min_height
width
height
haarcascade_frontalface_alt2.xml
cvLoadImage
cvResize
cvSaveImage
报名照片.JPG
背景必须是白底或蓝底
```

`haarcascade_frontalface_alt2.xml` 说明人脸检测用的是 OpenCV 自带的 alt2 级联，不是自训练模型。这决定了它的能力边界：正脸检出率高，侧脸、遮挡、过度美颜会漏检。

## 3. 参数

`photo.ini` 全文只有 58 字节，**里面没有任何宽高**：

```ini
[PhotoInfo]
s_min=0.05
s_max=0.1
i_min=0.1
i_max=0.7
```

用 `GetPrivateProfileStringA` 读出来，四个值分别对应：

| 键 | 含义 | 用途 |
|---|---|---|
| `s_min` / `s_max` | 人脸框宽度 / 画面宽度 的允许区间 | Haar 检出后人脸占比校验，太大太小都拒 |
| `i_min` / `i_max` | 背景亮度归一化区间 | 白底 / 蓝底判定 |

**295×413 不在 ini 里**，它硬编码在 exe 的 `.rdata`（`min_width` 字符串旁边跟的就是 295），输出尺寸同理。所以想改尺寸只能改代码，不能改配置——这也意味着不同省份如果换了 exe 版本，尺寸和编码参数都可能变，`photo.ini` 靠不住。

`min_*` 是输入门槛，`width/height` 是输出尺寸，两者数值相同，意味着：**输入不能小于输出**，即官方明确禁止把低像素照片放大使用（《使用说明.doc》里也写了这句话）。

## 4. 处理流程

```
读 photo.ini
  ↓
cvLoadImage(用户选择的图)
  ↓
if (w < 295 || h < 413) → 弹窗拒绝，流程终止
  ↓
Haar 检测：人脸数量 != 1 → 弹窗拒绝
  ↓
底色判定：白底 or 蓝底，否则拒绝
  ↓
cvResize(295, 413)
  ↓
cvSaveImage(报名照片.JPG)  ← 只传 2 个参数，params = NULL
```

几个细节：

- **不做裁剪**。它是直接 `cvResize` 拉伸到 295×413，所以原图比例不对时人脸会被压扁。本项目的 `crop_to_ratio` 先按比例居中裁剪再缩放，输出更自然——这是有意的改进，不是遗漏。
- **不做美化**。没有任何磨皮、提亮、美白代码路径。
- **固定输出文件名** `报名照片.JPG`（大写扩展名，Windows 不敏感）。
- **质量参数不在 exe 里**。exe 里 `cvSaveImage` 只有两处调用（文件偏移 `0x2dfe`、`0x3102`），两处都只 push 了 filename 和 image 两个参数；`highgui100.dll` 的 `cvSaveImage`（RVA `0xad08`）在往下调编码器时，params 位置 push 的是 `0`。所以质量值由库内部默认决定——**这也是静态分析推不出具体数值、必须靠真样本反解的原因**。第一版在这里猜了个 75，是错的。

## 5. 输出文件特征（实测，非推测）

> 这一节原来写的是「无签名 ⇒ 服务端只校验四类」，那是**纯静态推断，没跑过真机，结论是错的**。
> 2026-11-01 拿到一份真实通过国考报名确认的文件后逐段解出来，实际特征如下。

| 特征 | 值 |
|---|---|
| 尺寸 | 恒定 295×413 |
| 格式 | baseline JPEG（SOF0） |
| 体积 | 约 6–7 KB |
| 亮度量化表 | IJG 标准表 ×1.25，首值 20 |
| 色度量化表 | IJG 标准表 ×1.25 |
| Huffman 表段长 | 31 / 181 / 31 / 181（标准表，非优化表） |
| 采样因子 | Y 2×2，Cb/Cr 1×1 → 4:2:0 |
| JFIF | version 1.1，`units=1`，96×96 dpi |
| EXIF / ICC / 渐进 / DRI | 均无 |
| 数字签名 / 水印 / 隐写段 | 无（**这一条仍然成立**） |

关键修正：**「没有签名」不等于「无法分辨」。**

JPEG 不需要藏任何东西，因为编码参数本身就是指纹：

- 量化表唯一对应一个质量系数。`quality=40` 在 libjpeg 里走 `5000/40 = 125%`，标准表 16 变成 20，其余值同比放大后取整。这个组合不是随便什么软件都会产生的——Pillow 的 `optimize=True` 会连 Huffman 表一起改掉，段长从 31/181/31/181 变成 28/62/27/48。
- JFIF 头里的 DPI 是另一个极易忽略的标记。官方写 `96×96`，而 Pillow 默认写无单位的 `1×1`。两者在任何看图软件里都没有区别，只在前 20 个字节里能看出来。

反解过程很直接：把样本的 DQT 段读出来，和 IJG 标准表逐值相除，比值稳定在 1.25；再用 libjpeg 的换算反推，`5000/quality = 125` → `quality = 40`。

## 6. 服务端到底校验什么（2026-11-01 修正）

**原来的结论（错的）**：只校验扩展名、宽高、体积、底色，满足即等价。

**实测事实**：一个 295×413、10,007 字节、蓝底、baseline、无 EXIF 的文件——四项全对——被拒绝，提示「您的照片未经过照片处理工具处理」。而同样尺寸、同样格式、同样底色的另一个文件通过了。两者唯一差异就是上面那张表里的编码参数。

所以校验至少包含编码层，可能具体是其中一项或几项的组合（无法从外部确定是哪一项，没有做黑盒逐项消融）。工程上的结论是确定的：

> **把 DQT / DHT / JFIF 三项对齐到官方样本，就能通过。**

`validate.check_encoder_fingerprint()` 就是按这个做的：三项任一不符就给警告，`--strict` 下直接失败。

顺带一提，这也解释了为什么「用 PS 按规格存一张」有时过有时不过——PS 的量化表和 DPI 设置取决于导出参数，撞上了就过，没撞上就不行。

## 7. 为什么本项目不照抄 cvResize

官方直接拉伸，遇到 4:3 或 16:9 的原图会把人脸压扁。虽然能过机器校验，但审核人员肉眼看到变形照片观感很差。

本项目改成：按目标比例居中裁剪（顶部多留 28% 余量给头部）→ LANCZOS 缩放。输出同样 295×413，但不变形。

## 8. 局限与未验证项

- **人脸检测没有复刻**。Haar 级联需要 OpenCV，装包体积 100 MB+，为一个布尔判断不值得。本项目改用「中部纹理 vs 边缘纹理」的启发式，只能发现纯色块这种明显错误。若官网以「未检测到人脸」驳回，只能换照片。
- **底色判定是抽样，不是全图**。取四角 12% 区域的中位色，对纯色背景准确，对渐变背景会误判。
- **不同省份的 exe 可能参数不同**。本例是国考/人社部版本（295×413）。部分省考、行业考试用 413×579、480×640 等，这些尺寸**不在 `photo.ini` 里**（见第 3 节），只能从当次公告或各自的 exe 里取，本项目用 `--size` 覆盖即可，但没有逐一验证过。同理，各省的 exe 版本若不同，量化表 / DPI 也可能不同——真遇到过不去的，用 `--check-only` 和该省一份已通过审核的照片对比编码指纹。
